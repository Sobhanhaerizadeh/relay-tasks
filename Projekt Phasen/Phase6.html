CONTRIBUTING.md
01 PR
Niemals direkt auf main pushen
Immer einen eigenen Branch erstellen → PR öffnen → warten bis jemand approved → dann mergen.
02 @mention
Fremden Code geändert? Autor im PR erwähnen
Wer Code von jemand anderem ändert, schreibt @username im PR und wartet auf dessen Approval.
03 .env
Keine Passwörter oder Keys in Git
Alles Geheime gehört in die .env Datei — niemals direkt in den Code schreiben.
04 pip
Neues Paket installiert? Sofort in requirements.txt
Jedes neue Paket gehört im selben PR in die requirements.txt — sonst kann niemand das Backend starten.
05 issue
Jeder PR schließt sein Issue
In die PR-Beschreibung Closes #<nummer> schreiben — dann schließt GitHub das Issue beim Mergen automatisch.
06 CI
Erst mergen, wenn der Haken grün ist
Sobald #27 gemergt ist, laufen die Tests bei jedem PR automatisch. Rotes ✗ → erst reparieren, dann mergen.
07 alembic
Neu · Datenbank ändern? Nur mit Migration
Ab #29: Wer ein Modell ändert, legt im selben PR eine Migration an (alembic revision --autogenerate). Nach jedem git pull: alembic upgrade head. Niemals relay.db löschen, um einen Fehler zu „reparieren“.
08 403
Neu · Rechte prüft immer das Backend
Ein versteckter Button im Frontend schützt nichts — jeder kann die API direkt aufrufen. Wer etwas nicht darf, bekommt vom Backend 403.

#29
Migrationen mit Alembic einrichten
Das Problem: create_all legt nur fehlende Tabellen an — neue Spalten in einer bestehenden Tabelle kommen nie an. Ohne Migrationen müsste jeder bei jeder Änderung seine relay.db löschen. Deine Aufgabe: Alembic einrichten und create_all aus main.py entfernen.
# im Ordner backend/
pip install alembic # → requirements.txt
alembic init migrations
# migrations/env.py — Alembic soll unsere Modelle und unsere DB kennen
from database import Base, DATABASE_URL
import models # registriert alle Tabellen

config.set_main_option("sqlalchemy.url", DATABASE_URL)
target_metadata = Base.metadata

# in beiden context.configure(...)-Aufrufen ergänzen — SQLite kann sonst keine Spalten ändern
render_as_batch=True
# erste Migration = die Tabellen, die es schon gibt
alembic revision --autogenerate -m "users und tasks"
alembic upgrade head
Tipp: Die erzeugte Datei in migrations/versions/ immer durchlesen — Alembic rät nur. Wer schon eine relay.db hat, löscht sie einmalig vor alembic upgrade head. Im backend/README.md den Startbefehl ergänzen: erst alembic upgrade head, dann uvicorn.
# Fertig, wenn …
✓ relay.db löschen → alembic upgrade head → Tabellen users, tasks, alembic_version existieren
✓ main.py enthält kein create_all mehr, Backend startet normal
✓ Register, Login und /tasks funktionieren wie vorher
feature/29-alembic ⚡ Fundament für alle DB-Änderungen

#31
Admin-Rolle in der Datenbank
Das Problem: Das Backend weiß nicht, wer Admin ist. Deine Aufgabe: die Tabellen roles und user_roles aus unserem Datenbankmodell bauen, die Rolle admin anlegen und /me sagen lassen, ob der User Admin ist.
# models/role.py
Role → role_id (PK) · name (unique)
UserRole → user_id → users.user_id · role_id → roles.role_id (beide zusammen = PK)

# Migration: nach create_table die Rolle gleich mit anlegen
roles = op.create_table("roles", ...)
op.bulk_insert(roles, [{"name": "admin"}])
# core/roles.py — wird von #33 wiederverwendet
def is_admin(user: User, db: Session) -> bool:
    return db.scalar(
        select(UserRole).join(Role)
        .where(UserRole.user_id == user.user_id, Role.name == "admin")
    ) is not None
# backend/make_admin.py — einen User zum Admin machen
python make_admin.py sobhan@example.com

# /me antwortet jetzt mit
{"email": "sobhan@example.com", "is_admin": true}
Warum ein Skript statt eines API-Endpunkts? Dann kann sich niemand über die API selbst zum Admin machen — nur wer Zugriff auf den Server hat. is_admin kommt in MeResponse. Beide Modelle in models/__init__.py importieren.
# Fertig, wenn …
✓ alembic upgrade head → Tabelle roles enthält "admin"
✓ normaler User → /me zeigt is_admin: false
✓ make_admin.py → neu einloggen → /me zeigt is_admin: true
✓ make_admin.py zweimal für denselben User → kein Fehler
feature/31-admin-role → nach #30

# tests/conftest.py — jede Test-Funktion bekommt eine leere DB
engine = create_engine("sqlite://", connect_args={"check_same_thread": False}, poolclass=StaticPool)
TestSession = sessionmaker(bind=engine)

@pytest.fixture
def client():
    Base.metadata.drop_all(engine)
    Base.metadata.create_all(engine)

    def test_db():
        with TestSession() as db:
            yield db

    app.dependency_overrides[get_db] = test_db
    limiter.reset()
    yield TestClient(app)
    app.dependency_overrides.clear()
# tests/test_register.py
✓ neuer User → 200, gleiche E-Mail nochmal → 400

#33
Aufgaben bearbeiten & löschen — nur für Admins
Das Problem: Aufgaben können nur angelegt werden. Deine Aufgabe: PATCH und DELETE bauen — und dafür sorgen, dass nur Admins sie benutzen dürfen. Normale User bekommen 403.
# core/dependencies.py
def require_admin(current_user: User = Depends(get_current_user),
                  db: Session = Depends(get_db)) -> User:
    if not is_admin(current_user, db):
        raise HTTPException(status_code=403, detail="Nur Admins dürfen das")
    return current_user
# routers/tasks.py
PATCH /tasks/{task_id} # TaskUpdate: alle Felder optional, dazu status
DELETE /tasks/{task_id} # → 204

# nur die Felder ändern, die wirklich mitgeschickt wurden
for key, value in changes.model_dump(exclude_unset=True).items():
    setattr(task, key, value)
Reihenfolge der Prüfungen: kein Token → 401, kein Admin → 403, Aufgabe gibt es nicht → 404. require_admin läuft also vor der Suche nach der Aufgabe — so kann ein normaler User nicht einmal herausfinden, welche IDs es gibt. status darf nur open, in_progress oder done sein.
# tests/test_admin.py — Admin im Test: UserRole direkt in die Test-DB schreiben
✓ PATCH / DELETE ohne Token → 401
✓ PATCH / DELETE als normaler User → 403 und die Aufgabe ist unverändert
✓ Admin ändert nur den status → Titel bleibt gleich
✓ Admin löscht → 204, danach fehlt sie in GET /tasks
✓ unbekannte ID als Admin → 404
✓ {"title": null} oder status "fertig" → 422, kein 500er
# Fertig, wenn …
✓ alle Tests oben grün
✓ in Swagger (/docs) tauchen PATCH und DELETE auf
feature/33-admin-edit-delete → nach #31 + #32 ⚡ Erste echte Berechtigung

Dashboard: alle Felder speichern & anzeigen
Das Problem: Das Formular hat Beschreibung, Priorität und Datum, aber das Dashboard schickt nur den Titel ans Backend. Sobald #30 gemergt ist, nimmt das Backend alle Felder an. Deine Aufgabe: services/api.ts, components/TaskModal.tsx und pages/Dashboard.tsx.
// services/api.ts
export type ApiTask = {
  task_id: number · title: string · status: string · owner_id: number
  description: string | null
  priority: 'low' | 'medium' | 'high'
  due_date: string | null // "2026-12-24"
  created_at: string
}

// createTask schickt jetzt alles mit
body: JSON.stringify({ title, description, priority, due_date })
Achtung im TaskModal: Ohne Datum wird gerade „heute“ eingesetzt (dueDate || new Date()…) — stattdessen null schicken, sonst ist jede Aufgabe ohne Datum sofort „fällig“. Auf der Karte zeigen: Beschreibung (max. 2 Zeilen, line-clamp-2), Priorität als farbiges Badge, Datum mit toLocaleDateString('de-DE') — rot, wenn es vorbei und die Aufgabe nicht erledigt ist. Dashboard.tsx und api.ts hat Sobhan zuletzt geändert → @Sobhanhaerizadeh im PR erwähnen.
# Fertig, wenn …
✓ Aufgabe mit allen Feldern anlegen → Seite neu laden → alles ist noch da
✓ Aufgabe ohne Datum → kein Datum auf der Karte
✓ Datum in der Vergangenheit → rot

// services/api.ts — drei neue Funktionen
getMe() // GET /me → { email, is_admin }
updateTask(id, changes) // PATCH /tasks/{id} → ApiTask

// Dashboard.tsx
